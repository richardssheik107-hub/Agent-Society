# Phase 7

Evaluation Harness & Trajectory Dataset

## Goal

Phase 7 turns the verified single-agent lunch loop into a repeatable, inspectable benchmark. One `ScenarioConfig` creates a fresh `WorldState` per episode; `EpisodeRunner` reuses the existing `ClosedLoopStep`; `TrajectoryRecorder` observes each step; `MetricsAggregator` computes objective statistics; and the report writer emits JSON and Markdown summaries. Evaluation must not change decisions, rules, state transitions, or events.

The frozen v0.1 baseline is **Single-Agent Real Closed-Loop**: executable actions are `MOVE`, `BUY`, and `EAT`; a triggered decision uses at most one application-level model call (one provider request in the real-provider path); `ContextCompiler` produces bounded compact context; environment, rules, reducer, and event generation use **zero LLM calls**. The Phase 6.5C real run reached `MOVE restaurant → BUY meal → EAT meal` in three provider requests. Alice finished at the restaurant with money `80.0`, hunger `0.2`, no meal, and restaurant stock `9`. The full suite at that point had **210 passing tests**. This is a historical one-episode baseline, not the Phase 7 pilot result.

## Why evaluation before more features

A successful demonstration does not say how often a policy succeeds, how long it takes, whether it repeats or proposes rejected actions, or what the model actually saw. Phase 7 records each local observation and compact decision context beside objective before/after world snapshots, deterministic rule outcomes, events, provider usage, and latency. It then aggregates multiple episodes under one fixed scenario. This establishes a comparison boundary before adding behavior types or varying context policy.

Success is decided from `WorldState`, not from a model-generated explanation or an LLM judge. The evaluation package may invoke only the injected `DecisionClient` through the existing decision path; it adds no summarizer, repair call, retry, or judge. Wall-clock timestamps describe artifacts but do not affect scenario state, rule outcomes, or decision context.

## Trajectory Schema

The schema constant is `trajectory_schema_version = "0.1"`; each serialized step and episode, as well as the dataset manifest, carries `schema_version: "0.1"`. A step has a stable `episode_id` and one-based `step_index`. Serialized keys are `state_before`, `observation`, `context`, `proposal`, `intent`, `rule_allowed`, `rule_reason_code`, `effects`, `event`, and `state_after`, followed by the accounting fields below. `state_before` and `state_after` are JSON objects with `time`, `locations`, `people`, and `venues`, not Python `repr` strings. `observation` is the actual local projection delivered to the agent, not the full world. `proposal` holds parsed `action`/`target`; `intent` adds `actor_id` and `params`; `effects` is an array of typed objects; `event` holds `event_type`, `actor_id`, `action`, `target`, `success`, and `reason_code` (plus `event_id`).

Per-step accounting includes application decision calls, provider request attempts, context and prompt character counts, decision latency, available input/output/reasoning token counts, visible final-content character count, and returned provider model. Missing provider usage is represented as missing data, never silently as zero. The default trajectory stores neither the full prompt nor raw visible response. An explicit `record_prompt=True` may retain a prompt for local debugging; such a dataset must mark `contains_raw_prompt=true` in its manifest and must not be shared without review. Hidden `reasoning_content` text, authorization headers, API keys, and `.env` contents are never recorded. Numeric reasoning-token usage is permitted; raw reasoning text is not.

The exact accounting keys are `decision_call_count`, `provider_request_count`, `context_chars`, `prompt_chars`, `decision_latency_seconds`, `input_tokens`, `output_tokens`, `reasoning_tokens`, `visible_content_chars`, and `provider_model`. For the real adapter, a provider attempt is counted immediately before the HTTP POST, including a POST that ends in a transport or HTTP error; a scripted client records zero provider requests. A failed attempt without a completed action is represented in `EpisodeResult`, not as a fabricated `StepTrajectory`.

`validate_trajectory()` checks one-based consecutive indices and world continuity: step *n*'s `state_before` must equal step *n−1*'s `state_after`. Rejected actions preserve the world exactly and emit `ACTION_REJECTED`. Accepted `MOVE`, `BUY`, and `EAT` actions have at least one effect and emit `MOVED`, `PURCHASED`, and `ATE`, respectively. These invariants concern serialized objective state, not the text of the model response.

## Episode Result

`EpisodeResult` identifies the scenario, episode, decision policy, model, and context policy (`baseline_compact` for v0.1); `seed=None` is reserved for the current deterministic simulator. It records success, a machine-readable `termination_reason`, decision count, accepted/rejected/invalid/provider-error counts, final structured state, events, steps, total available token usage and latency, and maximum context/prompt lengths. Current lunch success means `hunger <= 0.2` **and** meal inventory equals `0` after a decision. The fixed lunch scenario starts Alice at home with money `100.0`, hunger `0.8`, empty inventory, and restaurant meal price `20.0`/stock `10`; it allows at most five decisions.

Termination reasons are `GOAL_REACHED`, `MAX_DECISIONS`, `INVALID_MODEL_OUTPUT`, `INVALID_ACTION`, `PROVIDER_ERROR`, `TIMEOUT`, and `ARCHITECTURE_ERROR`. They separate policy failure from provider failure and harness defects. One episode's provider failure is recorded without retrying that episode and need not abort subsequent episodes; an architecture error is reported rather than reclassified as a policy result. Stable display IDs use `lunch-000001`, `lunch-000002`, and so forth. Each episode receives a fresh world, so episode 2 begins with restaurant stock `10` even when episode 1 ends at `9`.

`INVALID_ACTION` is a proposal rejected by decision parsing/availability checks before execution, such as an unadvertised `WAIT`; it produces no rule event. A valid `MOVE`/`BUY`/`EAT` proposal can instead reach `RuleEngine` and be rejected with a reason such as `NOT_AT_SELLER`; this is a recorded step with an `ACTION_REJECTED` event and unchanged world. Invalid JSON is `INVALID_MODEL_OUTPUT`, not a rule rejection.

## Metrics

`MetricsAggregator` accepts `list[EpisodeResult]` and returns `BenchmarkMetrics`. The report covers episode total/success and completion rate; mean and median decisions; accepted and rejected actions plus rejection rate; invalid-output, provider-error, and timeout counts; average and maximum context/prompt characters; average input/output/reasoning tokens and latency per decision; latency p50/p95; and total provider requests. It also counts proposed actions, rejection reason codes, event types, and compact trajectory signatures such as `MOVE>BUY>EAT` or `BUY!NOT_AT_SELLER>MOVE>BUY>EAT`.

Completion rate divides successes by total episodes. Rejection rate divides rejected actions by accepted plus rejected actions. Context, prompt, and latency averages use completed `StepTrajectory` records; a provider or parser failure before a completed step still contributes to episode-level failure and provider-request counts. Each token average uses only completed steps with a non-null value for that particular field; the real pilot reported all three token fields for all nine completed steps. Consumers should inspect nullable per-step token fields rather than infer that unavailable usage was zero. Latency percentiles sort completed-step latencies and linearly interpolate at position `(n - 1) × percentile` (p50 or p95), without NumPy. The report is descriptive: a small three-episode pilot is not a statistical estimate of general model quality.

## Offline Benchmark

The gate before any new real request is a sequential, fully offline scripted benchmark of **20 fresh lunch episodes**. The expected deterministic path is `MOVE>BUY>EAT` for every episode: 20 successes, completion rate `1.0`, average decisions `3.0`, zero rule rejections, and that signature appearing 20 times. A separate small scripted rejection case uses `BUY>MOVE>BUY>EAT`: the first action yields `NOT_AT_SELLER`, the state remains unchanged, and the eventual episode still succeeds. Unit tests cover recorder ordering, before/after snapshots, events, absence of secrets and hidden reasoning, fresh-world reset, metric arithmetic, and trajectory validation. These are acceptance expectations; measured Phase 7 outcomes belong in **Results** below.

## Real Provider Pilot

After the full offline suite, scripted benchmark, and trajectory validation pass, run exactly **three sequential real-provider episodes once**. `REAL_EPISODES=3` and `max_decisions=5` bound the pilot to at most 15 provider requests; a three-step success in each episode would take nine. There is no application retry, no parallel Ray request, no prompt engineering during the pilot, and no additional episodes to replace failures. The decision adapter retains Phase 6.5C's verified minimal request body: **`model` + `messages` only**—no `thinking`, `temperature`, or `max_tokens` fields.

Each episode records its own result and can continue past an episode-level provider error. A legitimate model policy failure does not invalidate the harness: 2/3 or even 0/3 successful episodes can still be a valid Phase 7 measurement. Three provider failures instead require a visible provider-instability finding. The pilot prints only compact episode outcomes and a summary, not full context, prompt, response reasoning, or secrets. Every real step must stay under the existing context hard budget.

## Results

The final full offline suite passed: **234 tests**, with three pre-existing warnings. The 20-episode scripted smoke produced **20 successes**, completion rate **1.0**, average decisions **3.0**, zero rejections, and `MOVE>BUY>EAT` as the top trajectory with count **20**. Trajectory validation passed. A separate three-episode rejection script succeeded each time along `BUY!NOT_AT_SELLER>MOVE>BUY>EAT`; its rejection rate was **0.25**. Each episode used a fresh world.

The one-time, sequential real-provider pilot completed all **3 episodes successfully**, each along `MOVE>BUY>EAT`. It made **9 provider requests** total, with average **3.0 decisions** per episode, completion rate **1.0**, rejection rate **0**, invalid-output count **0**, provider-error count **0**, and timeout count **0**. Across completed decision steps, average context length was **289.0 characters** (maximum **334**), average prompt length **576.0 characters** (maximum **621**), input tokens **173.0**, output tokens **158.9**, reasoning tokens **147.6**, and decision latency **5.509 seconds** (p50 **5.557**, p95 **7.787** seconds). The manifest names the requested `ark-code-latest` alias; every completed step records returned `provider_model="glm-5.3"`. `MOVE`, `BUY`, and `EAT` each appeared three times; `MOVED`, `PURCHASED`, and `ATE` each appeared three times; there were no rejection reasons. These reasoning figures are usage counts only; no hidden reasoning text is retained. Environment, rules, reducer, and evaluation judge each made **0 LLM calls**. This three-episode result is distinct from the historical Phase 6.5C one-episode acceptance and is too small to establish a general success rate.

The real-pilot `trajectories.jsonl` contains **9 step records** and there are **3 episode JSON** files. Each episode began with restaurant meal stock **10** and ended with stock **9**, confirming fresh-world reset. The post-run audit covered **33 files** under `run/evaluation/`: zero matches for the exact configured provider key, authorization/Bearer text, or `reasoning_content`; zero serialized prompt fields. The dataset schema is **0.1**. `run/evaluation/` is ignored by Git; upstream `third_party/AgentSociety` had empty status and diff. Trajectory validation, privacy checks, offline gates, the one-time real pilot, and the final test suite all passed. Phase 7 did not commit or push these changes.

## Failure Categories

Harness failures are classified as `TRAJECTORY_SCHEMA`, `RECORDER`, `EPISODE_RUNNER`, `WORLD_RESET`, `METRICS`, `VALIDATION`, `OFFLINE_BENCHMARK`, `REAL_PILOT`, `SECRET_SAFETY`, or `ARCHITECTURE_VIOLATION`. Within an episode, the machine-readable termination reason distinguishes invalid model output, invalid action, provider error, timeout, maximum decisions, goal reached, and architecture error. Reports should preserve the failed command, error, root cause, and minimal fix rather than treating a provider outage as a rule or policy failure.

## Dataset Structure

`run/evaluation/offline/` and `run/evaluation/real_pilot/` are local, ignored output roots. Each contains `episodes/episode_XXXXXX.json` files with metadata, ordered steps, and final result; `trajectories.jsonl` contains exactly one serialized `StepTrajectory` per line; `summary.json` and `summary.md` contain aggregate metrics. `dataset_manifest.json` records schema version, scenario, creation time, episode and step counts, decision-client type, model, `contains_raw_prompt`, and `contains_hidden_reasoning=false`. No credential or authorization metadata belongs in any file. A post-run scan must check generated artifacts for keys, headers, and `.env` contents before sharing them.

The schema retains `context` as potential future supervised input and parsed `proposal` as potential output, with rule outcome and resulting state for analysis. Phase 7 does **not** implement SFT conversion, fine-tuning, LoRA, or training. Because `run/` is ignored, these records remain local; the results above can be recomputed from `run/evaluation/real_pilot/summary.json`, its three episode JSON files, and nine JSONL lines on this machine, but no public dataset is claimed.

## Future Local 8B Comparison

A future local 8B run must reuse the same scenario, fresh initial world, `ContextCompiler`, `RuleEngine`, terminal condition, trajectory schema, and metrics. Only the injected `DecisionClient` is replaced. Episode metadata holds `decision_policy_name`, `model_name`, `context_policy_name="baseline_compact"`, and a reserved seed so results can be compared without losing provenance. A rigorous comparison should predeclare the same episode count and stopping budget, record model decoding settings and tokenizer, and separate policy-success comparisons from hardware/network-dependent latency comparisons. Those controls are not new Phase 7 experiments. Context ablations such as `no-memory`, `recent-1`, or `recent-3` are not implemented in Phase 7; changing context policy requires a later, separately labeled experiment. No `CHAT`, `WORK`, multi-agent behavior, social graph, long-term planning, embeddings, RL, or new rule type is part of this phase.
