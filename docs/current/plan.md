## 一、最终目标与当前最重要的判断

我们的目标不是无限增加对象、状态或规则，而是建立一个**规则可维护、事实可追溯、行为可执行、长期结果可评价、成本可控制**的虚拟人系统。

```text
对象目录：世界中有什么，对象参数从哪里来
人物状态：现在拥有什么、需要什么、做到哪里
共享规则：什么条件允许动作，动作具体改变多少
模型决策：在给定事实与候选中选择下一步
持续执行：推进时间、保存结果、生成下一次观察
评估与成本：哪里正常、哪里失败、每完成一件事花多少
```

当前不再重复证明 Q3 的单步目录优势或 Q5 的虚拟索引扩展性。最紧迫的问题是：**对象存在但人物未拥有时，怎样合法获取、持久保存并在后续使用；合法、完成和人的行为适当性怎样分别评价。**

合并代码不等于科学问题全部解决，也不等于可以启动长时间付费运行。

### 5.2 固定状态面板的历史范围

历史固定范围为 **12 个冻结状态×2 条件×2 次重复＝48 单元、24 配对**，v1/v2 协议、旧提示及真实 session 冻结。已用许可不能转为本轮授权；不重跑 `q62-panel-real-v2-01`，不按中途结果增加样本。以下保留场景与控制要求用于解释原协议，不构成新的执行安排。

冻结场景覆盖游戏未拥有/已拥有、餐前/餐后、媒体进度、活动地点、餐食购买资源与休息工作条件等。保留正常与可执行状态，不能将只挑失败来保证 B 获胜的场景替换进原面板；实际清单以 PR #6 的冻结产物为准。

每个A/B配对从同一冻结快照复制出独立world，只提出并执行一个高层活动；执行结果不能流入下一配对。配对内AB/BA交替并用固定seed安排顺序；保存初态hash、候选hash及分配表。重复两次只能用于小规模探索，不是两个独立人群。

A保持原观察与提示；B只增加当前可执行活动/对象对。对象、规则、状态、先验、provider契约和输出限制固定；不同时加入近期摘要、采购新行为、禁止重复吃饭或关闭思考的新参数。场景答案、未来状态、评分标签不得进入提示或投影器。

### 5.3 评分必须独立于候选生成

主要比较以**实际RuleEngine在独立副本上的执行结果**为准，而不是“模型选了我们给出的候选，所以一定正确”。同时报告投影成员资格、启动接受、活动完成、commitment失败、状态不变量、上下文和成本。

统计至少并列呈现：计划数、已尝试数、有效提案数、拒绝数/有效提案数、接受数/有效提案数、完成数/有效提案数、完成数/计划数；完整配对分析与所有已分配单元的覆盖情况都保留。超时、未运行、无效输出不并入行为性拒绝；NA不补0。

同状态面板另列“A拒绝/B接受”“A接受/B拒绝”等不一致配对，以及按场景家族的分布。重复观测按场景汇总，不把同场景重复当完全独立样本。48次仅是探索预算；是否需要更大样本，在看清不确定性后另立协议，不边看结果边无限加样本。

### 5.4 预注册停止条件与结果分流

短链与固定面板的历史停止规则分别冻结，不在本轮重写。未来新协议若要调整故障分流，需要先明确版本、范围和预算，不能把新机制投回旧实验单元。

所有模式禁止retry、JSON修复、模型/endpoint切换、修改状态后补跑和脚本替代。出现未知发送状态先核对原记录，不重新发送。

结果允许四种结论：**有观察到的改善、无清楚差异、观察到退步、证据不足**。若B减少拒绝但代价过高，尝试紧凑表示属于下一份协议；若A/B都好，不能声称证明B必要；若B变差，保留A并查候选覆盖/表达；若规则或投影错误，先修工程，不调角色偏好遮掩。

原固定面板保留 `NO_CLEAR_DIFFERENCE`。M1.5 在 PR #7 对 22 个完整配对做离线状态后果审计，标签为 `EXPLORATORY_POST_HOC`；TRAVEL 与 MEAL 的宏活动粒度不同，需求、资金、精力和时间净变化不是整体人类效用，不能改写为 B 获胜。D-09 人工评价待审，模型不得代填。

## 六、M2：补齐“想玩游戏但没有游戏”的合法路径

这对应会议对象集问题的下一层：**目录里有对象，不等于人物有能力获取或使用它。**

本轮已经授权并实现独立实验活动 `ACQUIRE`，默认禁用。新 world 必须显式 `acquire_enabled=True`，配置保存为 `M2_ACQUIRE_V1`，重开按已保存值恢复；旧 seeded world 不能静默改成启用。D-02 生产默认语义依然未批准。

当前实现复用 `_check_purchase()`、`_buy()` 和原 commitment/control 生命周期。同地 start 零分钟成交；异地 MOVE 消耗原 travel_minutes，抵达先保存 ACTIVE BUY0，下一条明确 advance 再核对可用性、资金和库存并成交。即使原 advance 请求更晚，也在到达边界先返回；已经提交的旅行、需求和地点保留，购买与完成由事务及内层 savepoint 原子处理。

独立 M2 候选区分 `start_allowed` 与 `executable_now`，远程可启动不等于库存预约。范围限于可购买的非消耗性对象，不改食品 MEAL。获取完成不自动 PLAY；重开确认所有权后，只有下一次明确 PLAY 提案才按原规则使用游戏。

本轮验收覆盖已拥有、钱不足、零库存、途中下架/竞争、请求重放与冲突、暂停取消、真实持久恢复边界、BUY 进程退出和两 SQLite 连接竞争最后一件库存，并冻结旧提示、候选、状态与事件 hash。只声明 SQLite 参考实现的受测保证，不声称分布式 exactly-once。测试计数、完整 CI、AS2、审计和提交结果在[验收账本](acceptance.md)据实更新；未结束写 PENDING。

下一步仅建议申请独立小预算真实短链，核对“未拥有→ACQUIRE→持久恢复→下一次独立 PLAY”，场景、时间、请求上限和停止规则另行批准。**本轮真实请求为 0，D-02 产品语义未批准，人的行为适当性 NOT_TESTED。** 完整实现与边界见[M2 获取闭环](../studies/m2_object_acquisition.md)。

## 八、M4：尽早做一个本地小模型对照

模型替换不必等到30天实验。M1形成稳定面板、输出合同和成本口径后，即可核对硬件与接入条件，选择**一个**本地候选与既有远端参考对照，避免一次铺开多个模型。

记录模型标识/权重版本、量化、推理服务、上下文和输出预算、并发、温度及思考设置。相同世界、场景、合法性规则和候选投影不变；先分开报告模型差异与输入裁剪差异，不同时调多处追求成功。请求别名不是实际后端身份，未观察到的身份不补写。

按请求和每完成活动分别记录token、耗时及资源成本；本地成本不能直接视为0，价格依据未核对时只报实测资源和token、不编造金额。先单Agent短请求，达到预先批准的质量/成本条件后再扩并发。

输出：可用性、规则拒绝、状态利用、截断/超时、成本差异与失败样例。小模型结果不佳不立即削弱规则，也不能拿远端参考成绩替代本地证据。具体模型、硬件、预算和容忍差均待确认。

## 九、M5：长期行为分三层验收

### 9.1 先明确什么叫“正常”

| 层次 | 看什么 | 判定方式 |
|---|---|---|
| 硬事实一致性 | 钱/库存/所有权、时间、幂等、状态版本 | 确定性检查；任何真实违反必须调查 |
| 任务与进度连续性 | 看至第几集第几分钟、暂停/恢复、获取后使用 | 带覆盖标记的场景测试，不靠未触发时的true |
| 行为适当性 | 需求响应、义务履行、异常循环、偏好和分布 | D-05预先制定场景标准，存在分歧时人工复核 |

连续吃两次、显式重看一集或主动休闲不自动算错。异常循环应结合状态未改善、同一失败反复出现、没有新信息及持续窗口判断。不能靠强制几点工作/吃饭、硬禁重复或fallback WAIT制造好看轨迹。

### 9.2 覆盖先于时长

在独立新fixture中覆盖媒体暂停后续播、主线下一集与显式重看、所有权获取后使用、餐后仍有需求、物品下架与失败恢复。允许用脚本测试这些工程场景，但明确标注SCRIPTED；真实自主链中未选到WATCH，不能插WATCH后声称模型覆盖了追剧。

已有7/30天工程脚本保留，不重复当新模型研究。新版规则变化只做受影响回归及必要全库验收。

### 9.3 逐档扩展

建议顺序：短链→12次高层决策→半天/一天→多天；每档分别规定**模拟时间上限与模型请求上限**，不能把12次请求等价为一天。每档新授权，不继承无限运行许可。

分别记录计划/尝试/接受/完成、活动占用时间、即时动作链、provider等待、行为性空闲、预算截断和任务覆盖。游戏采购/正常行为标准未定前，不做声称开放自主生活的长跑。

进入下一档需要：没有未解释的状态或预算错误；故障可定位；目标任务覆盖达到预先要求；成本可接受。四次全部接受也不证明真人行为，多日脚本也不证明多日自主模型行为。

## 十、M6：把规则维护从虚拟索引推进到真实记录与变更负载

这是规则负责人可并行做的零模型工作。[Q5](../studies/q5_rule_scaling.md)已经说明不必给每个对象复制规则边，后续不用再重复同一个10M算术ID实验。

先确定最小合同：Object记录包含稳定ID/别名、type/capabilities、带单位与来源的属性、版本、可用性；Rule Template包含适用范围、前置条件、效果函数、失败码与版本。人物拥有量/观看进度是稀疏人物—对象状态，不塞回共享目录。规则写“如何计算”，对象参数写“变化多少”。

建议由小规模实际存储记录开始，例如1K→10K→100K；这里必须有payload、索引、读写和变更，不只虚拟ID。可以用声明为合成的参数化记录，不能冒充真实食品/游戏测量。只有业务需要并满足资源预算后再扩1M/10M，不预设必须建全世界目录。

必测负载：参数变化、模板更新、能力变化、例外条目、上架/下架、别名合并、版本迁移与并发库存；小目录先与朴素穷举结果对照。更新后哪些对象受影响应可解释，不默认编译全量Object×Rule边。

分别报告规则索引、对象payload、检索索引、人物—对象稀疏状态及进程总内存；延迟包括p50/p95、冷/热状态与更新成本。固定schema的常数索引不能推广为类型/例外数增长时仍常数。

有限运行目录、每次Top-K和动态上下架是三种不同控制量。先固定目录复现，再独立测试上下架策略；同时保留可用性与曝光次数，不能把低曝光误读为低偏好。世界事件必须版本化并留痕，不用临时“公司倒闭”解释随机删对象。
