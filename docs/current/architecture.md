# 规则体系：对象、状态、模型与后果分别由谁负责

本页是设计说明，实测状态见[问题索引](research_status.md)。图中某个模块存在不代表其全部能力已验证。

## 四个集合与三类事实

| 集合/状态 | 负责什么 | 不负责什么 |
|---|---|---|
| Object Set 对象集 | 正式 ID、类型、能力、价格/时长等带来源参数 | 不替模型决定偏好，不保证当前拥有 |
| Action Set 动作集 | 允许提出的行为及参数契约 | 动作名不等于当前合法 |
| Resource Set 状态集 | 人物需求、金钱、精力等事实 | 不把后台所有字段都强塞进 prompt |
| Rule Set 规则集 | 前置条件、参数化后果、状态一致性 | 不把群体日记频率写成强制日程 |
| 人物—对象状态 | 该人拥有多少、看了哪集、单集 offset、游玩多久 | 不依赖模型口头记忆维持真值 |

静态对象参数、当前人物状态、人物与对象的交互历史分开保存。食品名称不是热量真值，余额也不是模型生成文本。[相关术语](../reference/glossary.md)

## 共享规则如何产生不同效果

下面只是通俗公式，不引入新的生产规则或真实营养参数：

```text
购买：金额 -= 对象价格；人物持有量 += 1；卖家库存 -= 1
食用：人物持有量 -= 1；饥饿 = max(0, 饥饿 - 对象饱腹参数)
      摄入热量 += 对象热量参数
```

规则共享“怎么算”，各对象保存“改变多少”。购买扣钱和食用扣库存发生在不同步骤，不能两次扣同一笔钱。类型/能力只是找到适用规则，合法执行仍需位置、库存、所有权、冲突检查。[Q5 的边界](../studies/q5_rule_scaling.md)

## 从一个高层意图到持续活动

模型选择 MEAL 后，控制器在需要时移动、购买、进食；已拥有食物不再购买。每一步受规则约束，实际时间推进才累计进度。WATCH 默认解析下一未完成集，暂停和恢复保留实际观看 offset；显式重看不倒退主线。

SQLite 事务保存事实、活动、事件与命令结果；幂等 request_id 防止已提交后果重复。外部 HTTP 请求不能据此被宣称恰好发一次。AS2 适配器负责时钟、观察和 checkpoint 接口，不是另一份相互覆盖的事实真值。[Q6](../studies/q6_continuity.md)

## 三种“缩小信息”不要混为一谈

对象候选缩小目录暴露范围（Q3）；Resource 投影缩小可见状态字段（Q4 的下一步）；可执行活动投影列出当前合法的 activity/target（Q6.2 分支实现）。它们不是同一个 Top-K，也不能一次修改三者后统一归因。

Q6.2 用只读共享检查提供候选，提交时再检查。候选不是预约保证，更不是模型一定遵守的硬约束。其真实收益待测。

## 当前缺口

高层接口尚无购买游戏的入口；多天自主行为标准未冻结；合成参数的行为/生理合理性未联合校准；真实千万对象数据库和分布式事务未验证。不能靠手工修改初始状态隐藏这些缺口。[人工审核](../review/README.md)
